This page recognizes people who help improve the project through tutorials, labs, diagrams, examples, reviews, corrections, discussions, architecture critique, testing, documentation, and other meaningful contributions.

## Community Contributors

Community contributors will be listed here as the project grows.

Contributions may include:

- Tutorials
- Labs
- Architecture diagrams
- Minimal code examples
- Alternative patterns
- Documentation corrections
- Test improvements
- Accessibility improvements
- Security observations
- Architecture reviews
- Discussion contributions that lead to published learning material
- Cross-repository implementation references

A contribution does not need to be large to be recognized.

A clearer explanation, corrected diagram, reproducible example, or thoughtful technical critique can be just as valuable as a substantial code contribution.

## Recognition Guidelines

Contributor recognition should reflect meaningful participation rather than commit count alone.

Where practical, contributors may be recognized through:

- Git history
- Pull request attribution
- Release notes
- This contributors page
- Tutorial acknowledgments
- Lab acknowledgments
- Documentation credits
- GitHub's built-in contributor views

The repository should avoid creating an artificial ranking of contributors.

Different kinds of contributions provide different kinds of value.

## Attribution in Tutorials

When a contributor substantially authors or co-authors a tutorial, lab, diagram, or architectural analysis, the material may include an acknowledgment such as:

```markdown
## Contributors

- [Name](https://github.com/username) — original tutorial
- [Name](https://github.com/username) — architecture review
- [Name](https://github.com/username) — example implementation
```

Attribution should remain concise and should not distract from the learning material itself.

## Architecture and Discussion Contributions

Some of the most useful learning material may originate in Issues or Discussions rather than in a direct code contribution.

When a community discussion materially shapes a tutorial or architectural explanation, maintainers should make a reasonable effort to preserve that contribution through attribution or a link to the originating discussion.

A typical path may look like:

```text
Question
   ↓
Discussion
   ↓
Alternative ideas
   ↓
Experiment
   ↓
Tutorial or lab
   ↓
Contributor recognition
```

## Canonical and Alternative Contributions

Contributors may help improve both canonical and alternative patterns.

Recognition does not imply that every contributed architectural position has become canonical project guidance.

A contribution may be:

- Canonical
- Alternative
- Experimental
- Historical
- Editorial
- Corrective

The repository's [GOVERNANCE.md](../GOVERNANCE.md) explains how those classifications are handled.

## Becoming a Maintainer

Sustained contributors may eventually be invited to take on additional project responsibilities.

Signals may include:

- Consistent high-quality contributions
- Thoughtful review of other contributions
- Strong technical judgment
- Respectful participation in architectural disagreement
- Understanding of project boundaries
- Willingness to maintain existing material
- Reliable handling of community or security concerns

Maintainer responsibilities and selection are described in [GOVERNANCE.md](../GOVERNANCE.md).
