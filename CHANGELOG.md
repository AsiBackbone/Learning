# Changelog

Notable changes to AsiBackbone Learning are recorded here. This changelog begins with version 0.15.0; earlier history remains available through [GitHub Releases](https://github.com/AsiBackbone/Learning/releases) and the repository commit history.

Learning releases are archival and citation snapshots of educational material. They do not establish runtime compatibility or package support lines.

## [Unreleased]

### Changed

- Replaced the documentation logo, favicon, RSS feed image, and social cards with the open-book glyph from the AsiBackbone glyph family, which the organization site also uses. The social card now uses the canonical `AsiBackbone` spelling instead of "ASI BACKBONE". File names and image dimensions are unchanged.

### Added

- Published [Discovery Is Not Authorization: Using GitHub Issues to Govern AI-Assisted Development](docs/articles/2026/discovery-is-not-authorization-ai-assisted-development.md), a standalone article on why an AI coding agent that finds adjacent work while working an assigned issue is not thereby authorized to perform it. It follows one CSV-export issue through four discoveries, treats the issue as a work order with an outcome, acceptance criteria, non-goals, and constraints, classifies discoveries as blocking dependencies, separate work, security-sensitive findings, or noise, shows when to stop and ask, propose a linked follow-on issue, escalate privately, or drop a finding, describes what a follow-on issue should carry so its origin and evidence remain traceable, explains what GitHub references, sub-issues, issue dependencies, and closing keywords do and do not establish, treats issue-thread text from people without authority as data rather than instructions, and states when a lighter process is enough.
- Published [Your Retry Logic May Be Replaying an Authorization Decision](docs/articles/2026/retry-logic-may-replay-authorization-decision.md), a standalone article on why `HttpClient` resilience handlers, Polly pipelines, queue redelivery, and background-job retries decide when an attempt may run again but not whether an earlier authorization decision still applies. It follows one external folder share whose job is retried after a provider outage and a later legal hold, explains how retry layers multiply, places the eligibility check inside every retry loop that can outlive the decision, covers re-evaluation against authoritative state and explicit decision bounds when re-evaluation is not possible, separates retryable no-effect failures from ambiguous timeouts that must be reconciled, distinguishes a service-credential refresh from re-authorization, and states when ordinary retry plus current authorization is enough.

## [1.4.0] - 2026-10-24

### Added

- Added implementation-currentness metadata and reporting for implementation-dependent pages. `eng/implementation-baseline.json` now records the selected Learning baseline (AsiBackbone `v7.0.0`, NetCoreApplicationTemplate `v2.11.2`) that `tools/validate-asibackbone-api-references.cs` previously held as constants, and lists the pages that must declare a review. Pages declare `asibackbone_` or `netcoreapplicationtemplate_` `reviewed_ref`, `reviewed_on`, `reference` (`conceptual`, `api`, `runtime`, or `generated-template`), and an optional `next_review` trigger in their front matter, without adding package dependencies. The new `tools/validate-implementation-currentness.cs` rejects malformed, future-dated, or ahead-of-baseline reviews, reviews that disagree with a page's existing pin, implementation links on a reviewed page that are not pinned to the reviewed release or an exact commit, and review metadata on release-readiness records or pages marked historical, which keep their original pins. It reports each review as current, behind but within its trigger, or stale in the job summary; documentation validation reports stale reviews without failing, and the release gate fails on them with `--require-current`. The current API boundary, the production-host bridge, the five foundational tutorials and labs, and the package-integrity article participate initially, with reviews dated from the AsiBackbone 7.0 adoption, the production-host bridge, and the 7.1.0 currentness review. The tool only reports: it never rewrites framework-neutral teaching models to package APIs (#447).
- Published [You Don't Need to Roll Back What You Never Merged](docs/articles/2026/you-dont-need-to-roll-back-what-you-never-merged.md), a standalone article on de-risking .NET LTS migrations for applications derived from an upstream template or reference architecture. It explains a preserved upstream baseline, the application delta, a new baseline generated with the same inputs, and an isolated integration candidate; distinguishes the three-way integration model from a literal Git merge and compares merge, cherry-pick, patch, regeneration, and manual integration; qualifies the raw baseline (deterministic generation, option stability, baseline integrity, restore, build, test, format, security, container, and breaking-change review) before the integrated candidate; separates "runs on the new LTS" from "ready to adopt it"; covers continued fixes and security updates on `main`, drift management, objective adoption evidence, and discarding a failed candidate without reverting `main`; states that post-adoption rollback, data-migration recovery, and compensation still matter; covers contamination, drift, conflicts, duplicated work, and CI cost; compares branch, tag, generator, and vendor-snapshot baselines; explains when the pattern is excessive; cites current Microsoft support and compatibility documentation; and uses ReferenceApplication's NCAT 2.11.4 to 2.11.5 refresh as a bounded case study (#445).
- Added the [Cross-System Delegated Execution and Recipient-Local Trust](docs/case-studies/cross-system-delegated-execution-and-recipient-local-trust.md) reference architecture case study, which follows one fictional `records.export` from a governance decision in an independently operated request system, through a narrow, signed, sender-constrained delegated grant and a mutually authenticated handoff, to a receiving system that resolves the issuer and key from its own purpose-bound trust registry before verifying the signature, checks audience, operation, namespace, resource ownership and version, destination, request digest, presenter binding, lifetime under its own clock, delegation path, and revocation, maps the sender's role explicitly, applies its own policy to its own records, atomically claims a single use keyed on issuer and capability, and passes only a validated local command to a host-owned synthetic executor. It separates possession, signature validity, delegation, authorization, and execution; gives the sender decision, correlation, capability, recipient decision, execution attempt, and receipt identifiers one question each; applies clock skew to the start of the window only; rejects a delegation chain whose every hop verifies because the recipient never accepted the intermediary; distinguishes active, retired, revoked, and unknown keys for rotation, compromise, and historical verification; gives every dependency outage an explicit non-executing outcome; keeps evidence and coarse public responses on each side of the boundary; and states the residual risk of a consistently wrong issuer. It shows zero executor calls for an untrusted issuer behind a correct signature, a wrong audience, expired authority, a replayed second use, a recipient-local policy denial, resource version and classification drift, and an untrusted delegation chain in a decision/execution matrix, invariant traces, and illustrative tests, and compares same-system authorization, conventional service authorization, and reference-plus-introspection with a stopping rule for when cross-system delegated authority is unnecessary (#437).
- Added the [Shared Multi-Tenant Worker and Delayed Execution Isolation](docs/case-studies/shared-multi-tenant-worker-and-delayed-execution-isolation.md) reference architecture case study, which follows a fictional delayed `records.export` from a tenant-scoped request through authoritative tenant context, a bound export intent whose fingerprint includes the owning tenant, a request-time decision, a tenant-bound short-lived execution grant, durable job delivery carrying references only, a shared worker that authenticates as itself, and a protected host that resolves the tenant from its own records and revalidates current resource, destination, and policy state before a host-owned synthetic executor runs. It separates actor identity, application tenant, directory tenant, structured workload identity, and application (client) ID; rejects missing, repeated, or conflicting workload identity claims; compares worker-supplied tenant labels without ever using them; and shows zero executor calls for tenant, identity, audience, operation, resource, freshness, revocation, and replay failures in a decision/execution matrix, invariant traces, and illustrative tests. It distinguishes cross-tenant substitution prevention from worker-compromise isolation with an explicit threat analysis, compares the shared baseline with separately enforced partition identities, credentials, and placement, explains why separate names on shared credentials are not boundaries, treats tenant-scoped token exchange as an optional control, counts the operational cost of stronger isolation, declines to treat regional partitions as data-sovereignty evidence, and explains when one shared worker with ordinary tenant checks is the proportionate design (#436).
- Added the [Delayed Financial Payout and Ambiguous External Commit](docs/case-studies/delayed-financial-payout-and-ambiguous-external-commit.md) reference architecture case study, which follows a fictional `payout.submit` request from a bound payout intent through a governance decision, a short-lived single-use execution grant, durable job delivery, worker validation against current payout state and current policy, an atomic claim across grant, payout, and attempt that fences every context version validation relied on, a synthetic provider call, and attempt-specific reconciliation. It writes the decision, grant, daily-limit reservation, payout transition, and outbox row in one commit, separates the terms fingerprint from record versions, refuses to send when a claim or start write cannot be confirmed, states the conditions under which a claimed attempt provably sent nothing, and distinguishes a provider return from a rejection. It separates the historical decision, execution authority, claim, provider attempt, execution outcome, and reconciliation evidence; gives `PayoutId`, `CorrelationId`, `DecisionId`, `GrantId`, attempt, and provider idempotency key one question each; shows zero provider calls for every blocked pre-execution path; keeps the decision `Allowed` after a deterministic provider rejection; records a timeout after possible acceptance as `Unknown` and reconciles it by lookup before any new attempt; distinguishes delivery, execution, reconciliation, and authorization retries, and idempotency from authority replay protection, without claiming exactly-once execution; treats reversal as a separately governed operation; and includes a decision/execution matrix, invariant traces, illustrative tests, a simpler synchronous alternative, and a stopping rule. It uses no real payment provider and is not financial advice (#435).
- Published [An Allowed Decision Does Not Mean the Operation Succeeded](docs/articles/2026/allowed-decision-does-not-mean-execution-succeeded.md), a short, problem-first article that follows one merchant-payout suspension from proposal through decision, authority, claim, attempt, observed outcome, and reconciliation to separate decision truth from execution truth and evidence. It explains why the historical decision stays `Allowed` when execution fails and why rewriting it to `Denied` corrupts provenance; uses `NotStarted`, `Started`, `Succeeded`, `Failed`, and `Unknown` as illustrative states rather than a required enum; covers failure before execution, deterministic executor failure, a timeout after a possible external effect, and a lost completion record; distinguishes an operational retry from a materially new attempt that needs a fresh decision; treats compensation as a separately governed operation; and includes a decision/execution matrix, focused tests, a review checklist, and when a synchronous result and ordinary logs are enough (#418).
- Published [Idempotency Does Not Prevent Authority Replay](docs/articles/2026/idempotency-does-not-prevent-authority-replay.md), a practitioner guide that follows one queued refund delivered twice while the payment provider times out after accepting the first request, to separate authority replay from duplicate transport delivery, atomic capability consumption, operation identity and idempotency keys, and inbox/outbox deduplication, covering a compact `CorrelationId`/`DecisionId`/`CapabilityId`/`OperationId`/`IdempotencyKey` table, why reused authority is rejected even when the downstream operation is idempotent, why one-use authority does not justify blindly retrying an ambiguously completed side effect, unknown outcomes recorded separately from failures, reconciliation and what makes a later attempt materially new, why none of these mechanisms alone proves exactly-once execution, invariant tests for both directions, and when ordinary idempotency is enough (#417).
- Added the [Emergency Production Access and Break-Glass](docs/case-studies/emergency-production-access-and-break-glass.md) reference architecture case study, which follows a fictional `production.access.elevate` request from a declared incident through authoritative incident and on-call validation, pre-reviewed emergency profiles, independent approval with a designed single-operator alternative, a short-lived bounded-use grant, a host-owned access broker that re-validates expiry, revocation, scope, use count, and current incident state on every use, evidence written before each operation, and post-incident review that does not retroactively authorize anything. It presents emergency access as a separately designed authority path rather than a fallback when policy is down, defines behavior for each unavailable dependency, includes a decision/execution matrix and invariant tests with zero dry-run operations for every blocked path, and explains when an existing privileged-access platform, cloud control plane, or runbook should own the workflow (#416).
- Added [Retrofitting Governed Execution into an Existing ASP.NET Core Application](docs/aspnetcore/retrofit-governed-execution-into-an-existing-application.md), an advanced, phased playbook that continues from the decision-pipeline refactoring lab into a live application with a controller, an EF Core service and outbox, a background job, and an admin page. Ten phases, each with entry criteria, invariants, validation, and rollback conditions, cover justifying governance, inventorying every route to the side effect, characterization tests, a single protected-execution seam, a side-effect-free decision, shadow evaluation that cannot authorize execution (and when not to shadow), enforcement with fail-closed dependency handling and zero-execution tests, optional continuation features, transactions, idempotency, inbox, retries, and reconciliation, and a rollback switch that selects rule sets but cannot bypass the governed boundary. It includes a phase table, a stopping rule, and links to the production-host bridge for version-pinned integration details (#410).
- Added the Authorization-to-Governance Comparison sample, which runs one `DisableAccount` operation in a single ASP.NET Core application as endpoint authorization with operational logging, resource-based authorization through `IAuthorizationService` with a structured audit, and an explicit governance decision with separate decision and execution evidence and a host-owned execution boundary. The variants share fixtures and one recording side effect; eight scenarios and 49 tests show that authorization denial prevents execution in the first two variants, that every non-allowed governance outcome prevents execution in the third, and what evidence each records. The README's matrix compares code and state cost, outcomes, lifetime, evidence, and fit, and presents the variants as alternatives selected by requirements, not maturity levels. Linked from both architecture comparisons and the governed API lab (#407).
- Added the Governed Failure-Injection Trace sample, a companion to the policy simulation harness that runs a fictional export through intent, authoritative context, policy, continuation verification, scoped authority, host enforcement, and a counting executor. Thirteen named, non-interactive scenarios inject policy denial, unavailable context, missing acknowledgment, altered, expired, or mismatched receipts, expired, replayed, or misbound authority, and an entry-point bypass, and emit text or JSON traces naming the stopping stage and owner, authority issuance, executor invocation count, and separate decision and execution evidence. Tests prove zero executor invocations for every blocked path and exactly one for each valid path; receipt sealing is labeled a simulated boundary (#409).
- Added a version-pinned bridge from the five foundational Learning samples to the reviewed AsiBackbone 7.0 API boundary and NetCoreApplicationTemplate 2.11.2 host integration seams, including explicit partial mappings, host-owned enforcement responsibilities, and persistence/evidence choices. The AsiBackbone API-reference validator now requires the bridge's three pinned baselines and checks every Learning, AsiBackbone, and NetCoreApplicationTemplate link on the page against them (#408).

- Closed the remaining landing-page accessibility gaps in the custom stylesheet. Start here cards no longer lift on hover or focus when reduced motion is requested. ## [1.2.0] - 2026-10-03

### Added

- Published [How Application Architecture Complements Microsoft.AgentGovernance](docs/articles/2026/application-architecture-complements-microsoft-agent-governance.md), a practitioner guide that follows one AI-proposed refund through a host-owned control flow around `Microsoft.AgentGovernance`, covering authoritative context, verdict translation without Boolean collapse, workflow state, execution-time revalidation, proportional execution authority, failure semantics, evidence, and tests proving that non-allowed paths never reach the executor (#391).
- Published [Policy as Code in ASP.NET Core Without Overengineering](docs/articles/2026/policy-as-code-aspnet-core-without-overengineering.md), a selection guide that follows one ASP.NET Core refund endpoint through ordinary code, framework authorization, an in-process policy component, an embedded engine, and a remote decision service, with the pressures that justify each boundary and the obligations remote evaluation adds (#377).
- Published [Authorization vs. Approval vs. Acknowledgment: Which Decision Do You Actually Have?](docs/articles/2026/authorization-vs-approval-vs-acknowledgment.md), a practitioner guide that separates authorization, approval, acknowledgment, and execution permission, with an execution-time check and tests showing that none of them silently becomes permission to run a delayed operation (#375).
- Published [What Should an AI Tool Gateway Validate Before Execution?](docs/articles/2026/validate-ai-tool-call-before-execution.md), an ordered host-side acceptance checklist for AI tool calls with code and tests that prove rejected proposals never reach the executor (#371).

### Changed

- Pinned every workflow job to `ubuntu-24.04` instead of `ubuntu-latest`, which GitHub migrates to Ubuntu 26 beginning October 19, 2026. Moving to a newer runner image is now an explicit, reviewable change.
- Dependabot commit messages use the prefix `chore` with the dependency scope, producing `chore(deps): ...` instead of `chore(deps)(deps): ...`.

### Fixed

- Pull request and push link validation now accepts HTTP 503, so a transient outage on a third-party host no longer fails an unrelated change. The weekly scheduled run keeps the strict accept list and still reports links that stay unavailable.
- Refreshed the landing page's stale copy. **Recently added** now lists the three newest published articles under their current titles, and the Executable Samples card no longer uses a hard-coded sample count.
- `tools/validate-doc-metadata.cs` now fails the documentation build when **Recently added** does not name the newest published articles, newest first, with matching titles, or when it contains any list item that is not a plain article link.
- Markdown link validation no longer fetches `AsiBackbone/AsiBackbone` blob and tree URLs live. `tools/validate-organization-links.cs` already resolves each one against a fetched clone, and the live check only added transient GitHub 503 failures.
- [Constraint Composition and Policy Precedence](docs/governance/constraint-composition-and-policy-precedence.md) no longer describes its fail-closed defaults as "the current `AsiBackbone` 3.x default". It now names the `GovernancePolicyOptions.DenyWhenNoConstraints` and `TreatConstraintExceptionAsDenial` options, which still default to `true` in 7.x.
- `tools/validate-asibackbone-api-references.cs` now fails the documentation build when a Markdown page describes an AsiBackbone major version other than the current implementation ref as current, for example "the current `AsiBackbone` 3.x default". Release notes, the changelog, version-transition pages, and pages marked `asibackbone_status: historical` are exempt.
- The AsiBackbone API boundary pages and the landing page no longer call release tags immutable. A Git tag can be moved or deleted unless repository rules prevent it, so the 7.0 boundary page now says to resolve the tag to its commit SHA when a reference must not change. Published release records are unchanged.
